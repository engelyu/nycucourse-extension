# 選課網（cos.nycu.edu.tw）實際行為報告

實測日期：2026-09-20（115 學年第 1 學期加退選期間，選課系統開放中）。
用真實帳號做的實驗，每一項都記錄了送出的參數與伺服器回應。實驗結束時預排 54 筆、正式選課 9 門，與開始前完全相同。

實驗中**沒有**呼叫任何會動到已選上課程的操作。`deleteregist` 只用在自己剛登記、`sFlag` 不是 `F` 的課。

## 0. 名詞與狀態

| 狀態 | 判斷方式 | 意義 |
|---|---|---|
| 已選上 | `sFlag === 'F'` | 真的選上了。移除它＝退選 |
| 已登記 | `sFlag` 不是 `F` | 只是登記，要等分發。有志願群組時 `sFlag` 就是志願序數字 |
| 停修 | `PFW === 'W'` | 停修 |
| 鎖定 | `Lock === '1'` | 選課網不給退選（實測帳號裡的作業系統、導師時間、大一體育都是） |

## 1. 預排（setpreregist / deletepreregist / getpreregist）

### 1.1 預排完全不影響正式選課

**實測 E12**：把一門從來沒進過預排的課（516707 微分方程）直接 `setregist`，成功登記；登記後它也**沒有**被自動加進預排。
**實測 E17**：先登記 516713，再 `deletepreregist`，登記**完全不受影響**（`sFlag` 還是 1）。

結論：預排是純粹的「購物清單」，伺服器端不用它做任何事。正式選課只看 `setregist` 送出的欄位。

### 1.2 伺服器不檢查預排的任何欄位

`setpreregist` 會把 `menu_data` 字串原封不動存起來：

| 送出的 menu_data | 伺服器 | 選課網自己查得到嗎 |
|---|---|---|
| 正確的選單路徑 | 接受 | 查得到（status success） |
| `{}` | **接受** | **查不到（回傳空陣列）** |
| 亂填（type 9、dep_uid 全 0） | **接受** | **查不到** |

這就是 0.5.3 以前那個嚴重 bug 的成因：使用者看到課出現在預排，但選課網的加選視窗查不到它，等於完全沒用。**任何寫進預排的東西都必須自己保證 menu_data 正確，伺服器不會幫忙擋。**

重複加入同一課號會回 `[{status:'error', msg:'重複預選'}]`。

`setpreregist` 成功時回傳整列資料，欄位名稱是中文（課號、修課別、選單資訊、類別、新增日期、異動人員IP…），可以用來確認存進去的內容。

### 1.3 清單與效能

- `getpreregist` 的排序不是課號順序，也不是加入順序（實測新加入的三筆落在清單中間第 40–42 位）。要自己排。
- 實測延遲：單筆 `setpreregist` 45–525ms、`deletepreregist` 45–60ms、`getpreregist`（54 筆）約 1.5 秒。
- 平行送出可行：3 筆平行新增 477ms、平行刪除 82ms；同樣的操作循序做要 1009ms、987ms。**平行大約快 3 到 12 倍**，但仍建議限制同時 3 條，避免對學校伺服器造成負擔。

## 2. 正式選課（setregist）

送出欄位：`cos_id`、`cos_type_code`、`wType`、`wish`、`category_type`。

### 2.1 wish 決定結果，而且規則因課而異

選課網自己的程式（chunk-b47d6638 `cosRegist`）送出的 wish 就是登記後的 `sFlag`：

| 課程種類 | 選課網送出的 wish | 結果 |
|---|---|---|
| 有志願群組（`GroupUID` 不是 null） | 使用者選的志願序 1–6 | 已登記（第 N 志願） |
| 沒有群組、有人數上限 | `1` | 已登記，等分發 |
| 沒有群組、不限人數 | `F` | **直接已選上** |

**實測 E7**：沒有群組、有上限的課，伺服器其實**忽略**我們送的 wish：送 `''` 或 `9`，存進去的都是 `1`。所以這一類送什麼都一樣。

不限人數那一類沒有實測（送 `F` 會直接選上，之後只能退選，違反禁止事項）。但規則很明確：**送錯就會從「直接選上」變成「已登記」**，這就是 0.9.2 修掉的 bug（實變函數論 536700）。

### 2.2 修課別與採計方式：伺服器照單全收

**實測 E13**：對一門必修課（516707，真實 `cos_type_code` 是 1）宣稱 `cos_type_code: '2'`，伺服器就把它記成**選修**。`wType` 送 `'9'` 則被忽略，存成 `X`（看起來 wType 會驗證是否為該課允許的值）。

**實測 E14（最重要）**：核心課程 534000 初等應用統計（基本素養-量性推理）：

| 送出的參數 | 記錄結果 |
|---|---|
| `cos_type_code: E`、`wType: E`、`category_type: DF91BC7C…`（正確） | 核心、brief `Z102`、群組 `51CE2C18…`（核心課程-**基本素養**） |
| `cos_type_code: 2`、`wType: X`、`category_type: ''` | **選修**、沒有 brief、**沒有志願群組** |
| `cos_type_code: E`、`wType: E`、`category_type: ''` | 核心、brief `Z102`、但群組變成 `6D27BD78…`（核心課程-**領域課程**） |

也就是說：

- **採計方式是在登記當下由我們送出的欄位決定的**，不是課本身固定的屬性。
- **漏掉 `category_type`，課會被丟進錯誤的志願群組**，而畫面上的 brief 還是顯示原本的類別，從結果幾乎看不出來。志願序是在群組裡比的，丟錯群組等於志願序算在別的地方。

**規則：這三個欄位一定要原封不動使用 `getregistrationcourselist` 在「使用者選的那條選單路徑」下回傳的值，絕對不能自己推論或留空。**

### 2.3 已經登記的課不能直接改志願

**實測 E6**：對已經登記的課再送一次 `setregist`（不管 wish 是什麼），一律回 `[{status:'error', cmsg:'重複選課'}]`。要改志願必須**先 `deleteregist` 取消，再重新 `setregist`**。

⚠️ 我們現在的「改志願」按鈕就是直接再送一次，實際上一定失敗。這是擴充功能要修的 bug。

### 2.4 伺服器擋什麼、不擋什麼

| 情況 | 伺服器 | 說明 |
|---|---|---|
| 沒有修課權限、課程未開放 | **擋**：`{status:'error', cmsg:'無權限加選，課號(…)', errortype:'nopriority'}` | 實測 535516 軟體測試、110044 臨床解剖學 |
| 人數已滿（70/70） | **不擋**，照樣登記 | 實測 561068 生死學 |
| 衝堂，且課有人數上限 | **不擋**，`getregistrationcourselist` 也回 success | 實測 515609（conflict_num 3） |
| 衝堂，且課不限人數 | **擋**，`status: error`、`cmsg: 衝堂…` | 實測 516714、534501 |
| 修課別、採計類別填錯 | **完全不擋** | 見 2.2 |
| 同一群組兩門課填同一個志願序 | **完全不擋** | 見 3.2 |

推論：不限人數的課是「即選即上」，所以衝堂當下就擋；有上限的課是「登記後分發」，衝堂留到分發時處理。

## 3. 志願序群組（getCosCategoryWish）

### 3.1 資料結構

```
{ "<GroupUID>": {
    GroupName: "核心課程-基本素養", wType_cname: "核心課程",
    wish_limit: "6",     // 這個群組可以填幾個志願（多數 6，體育 5）
    cos_limit: "100",    // 這個群組最後可以選上幾門（學院共同／體育／微積分 = 1，核心／語言與溝通 = 100）
    wish: { "1": "0", "2": "0", "3": "2", ..., "F": "0" } } }
```

**`wish` 裡的值是「數量」，不是課號。**實測：在同一群組登記兩門課、都填第 3 志願之後，`wish["3"]` 從 `"0"` 變成 `"2"`。`wish.F` 則是這個群組已經**選上**幾門（實測帳號的微積分群組是 2、體育群組是 1）。

⚠️ 我們的 `wishOptions` 目前把這個值當成課號顯示「已填 563018」，是錯的。

選課網自己的用法（chunk-b47d6638）：

- 志願下拉選單只在 `wish.F <= cos_limit` 時出現，否則顯示「已達上限」。
- 每個志願序選項在 `wish[n] != 0` 時**變灰不能選**（已經用過的志願序不能重複用）。

### 3.2 伺服器不擋重複志願

**實測 E9**：同一個核心群組的兩門課（561068 生死學、534000 初等應用統計）都送第 3 志願，兩筆都成功，`wish["3"]` 變成 2。

也就是「一個志願序只能用一次」純粹是**前端規則**。我們的程式如果讓使用者重複填，送得出去，但分發時的行為沒有保證。**必須自己照選課網的規則擋。**

### 3.3 志願序在分發時的意義

API 沒有提供分發演算法。`getregistrationcourselist` 會回 `first_wish_reserved_num` 到 `fifth_wish_reserved_num`（各志願目前登記人數），可以顯示給使用者判斷。使用者提供的實務說法：同一門課若第一志願人數已超過上限，後面志願的人會直接被刷掉；因此**填錯志願序或沒填（被迫當成無志願）風險很高**。

## 4. 查詢（getregistrationcourselist）

- 參數：`cos_id` 加上選單路徑 `type / dep_category / college_no / dep_uid / group / grade / class`，以及 `category_type`。
- 回傳 `{ "<cos_id>": {...} }`；**查不到時回傳空陣列 `[]`**（例如選單路徑錯誤或該課不在那條路徑下）。
- 重要欄位：`status`（success/error）、`cmsg`、`cos_type_code`、`wType`、`GroupUID`、`num_limit`、`registered_num`、`conflict_num`、`first..fifth_wish_reserved_num`、`category_type`、`category_cname`、`brief`。
- **`blocked` 幾乎永遠是 `"1"`，不能拿來判斷能不能選**（實測 8 門課全部是 1，包含 status success 的）。要用 `status` 和 `cmsg`。
- `registered_num` 是登記人數，可能超過 `num_limit`（實測 516713 是 63/40）。自己登記之後這個數字不會立刻變動。

`preregistcourse`（列出某選單下的所有課）回傳的欄位更完整，包含 `brief`、`GroupName`、`category_*`、`crsoutline`、`classPri`、`degree`、`memo`。

## 5. 對「本機預排 + 一鍵匯出」架構的結論

### 5.1 可行，而且不需要碰預排

登記不需要預排（1.1）。所以本機清單可以直接匯出成一連串 `setregist`，預排只在「使用者想讓選課網自己的畫面也看得到」時才需要同步。

### 5.2 本機每一筆必須存什麼

因為採計方式是送出當下決定的（2.2），本機清單的每一筆都要存下**當初查詢時用的那條選單路徑**與**查到的結果**：

```
{ cosId, 選單路徑 menu{type,dep_category,college_no,dep_uid,group,grade,class},
  category_type, category_cname,        // 通識／核心類別，空字串也要明確存
  cos_type_code, wType,                 // 一律來自 getregistrationcourselist
  GroupUID, num_limit,                  // 決定送出時的 wish 規則
  wish,                                 // 有群組才需要，使用者選
  查詢時間 }
```

### 5.3 匯出前一定要重新查一次

存下來的值會過期（人數、開放狀態、甚至採計方式都可能被系所調整）。匯出流程應該是：

1. 對每一筆重新 `getregistrationcourselist`（用存下來的選單路徑）。
2. 查不到（回空陣列）或 `status` 是 error → **不要送**，明確告訴使用者哪一門、為什麼。
3. 查得到 → 用**這次查到的** `cos_type_code`、`wType`、`category_type` 組 `setregist`。
4. `wish` 依 2.1 的規則決定；有群組時要照 3.1 擋掉已用過的志願序。
5. 送出後**重新讀 `getregist` 驗證**，逐一比對 `sFlag` 是不是預期的值（不限人數應該是 `F`，其他應該是志願序或 `1`），把結果如實顯示。

### 5.4 絕對不能做的事

- 不能用預設值或猜測填 `cos_type_code`、`wType`、`category_type`。
- 不能在沒查到的情況下硬送。
- 不能對已經登記的課直接重送（會回「重複選課」）；改志願要先取消。
- 不能碰 `sFlag === 'F'` 的課。
