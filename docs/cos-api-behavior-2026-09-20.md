# 選課網（cos.nycu.edu.tw）實際行為報告

實測日期：2026-09-20（115 學年第 1 學期加退選期間，選課系統開放中）。
用真實帳號做的實驗，每一項都記錄了送出的參數與伺服器回應。實驗結束時預排 54 筆、正式選課 9 門，與開始前完全相同。

實驗中**沒有**呼叫任何會動到已選上課程的操作。`deleteregist` 只用在自己剛登記、`sFlag` 不是 `F` 的課。

## 0. 名詞與狀態

| 狀態 | 判斷方式 | 意義 |
|---|---|---|
| 已選上 | `sFlag === 'F'` | 真的選上了。移除它＝退選 |
| 已登記 | `sFlag` 不是 `F` | 只是登記，要等分發。有志願群組時 `sFlag` 就是志願序數字 |
| 停修 | `PFW === 'W'` | 停修 |
| 鎖定 | `Lock === '1'` | 選課網不給退選（實測帳號裡的作業系統、導師時間、大一體育都是） |

## 1. 預排（setpreregist / deletepreregist / getpreregist）

### 1.1 預排完全不影響正式選課

**實測 E12**：把一門從來沒進過預排的課（516707 微分方程）直接 `setregist`，成功登記；登記後它也**沒有**被自動加進預排。
**實測 E17**：先登記 516713，再 `deletepreregist`，登記**完全不受影響**（`sFlag` 還是 1）。

結論：預排是純粹的「購物清單」，伺服器端不用它做任何事。正式選課只看 `setregist` 送出的欄位。

### 1.2 伺服器不檢查預排的任何欄位

`setpreregist` 會把 `menu_data` 字串原封不動存起來：

| 送出的 menu_data | 伺服器 | 選課網自己查得到嗎 |
|---|---|---|
| 正確的選單路徑 | 接受 | 查得到（status success） |
| `{}` | **接受** | **查不到（回傳空陣列）** |
| 亂填（type 9、dep_uid 全 0） | **接受** | **查不到** |

這就是 0.5.3 以前那個嚴重 bug 的成因：使用者看到課出現在預排，但選課網的加選視窗查不到它，等於完全沒用。**任何寫進預排的東西都必須自己保證 menu_data 正確，伺服器不會幫忙擋。**

重複加入同一課號會回 `[{status:'error', msg:'重複預選'}]`。

`setpreregist` 成功時回傳整列資料，欄位名稱是中文（課號、修課別、選單資訊、類別、新增日期、異動人員IP…），可以用來確認存進去的內容。

### 1.3 清單與效能

- `getpreregist` 的排序不是課號順序，也不是加入順序（實測新加入的三筆落在清單中間第 40–42 位）。要自己排。
- 實測延遲：單筆 `setpreregist` 45–525ms、`deletepreregist` 45–60ms、`getpreregist`（54 筆）約 1.5 秒。
- 平行送出可行：3 筆平行新增 477ms、平行刪除 82ms；同樣的操作循序做要 1009ms、987ms。**平行大約快 3 到 12 倍**，但仍建議限制同時 3 條，避免對學校伺服器造成負擔。

## 2. 正式選課（setregist）

送出欄位：`cos_id`、`cos_type_code`、`wType`、`wish`、`category_type`。

### 2.1 wish 決定結果，而且規則因課而異

選課網自己的程式（chunk-b47d6638 `cosRegist`）送出的 wish 就是登記後的 `sFlag`：

| 課程種類 | 選課網送出的 wish | 結果 |
|---|---|---|
| 有志願群組（`GroupUID` 不是 null） | 使用者選的志願序 1–6 | 已登記（第 N 志願） |
| 沒有群組、有人數上限 | `1` | 已登記，等分發 |
| 沒有群組、不限人數 | `F` | **直接已選上** |

**實測 E7**：沒有群組、有上限的課，伺服器其實**忽略**我們送的 wish：送 `''` 或 `9`，存進去的都是 `1`。所以這一類送什麼都一樣。

不限人數那一類沒有實測（送 `F` 會直接選上，之後只能退選，違反禁止事項）。但規則很明確：**送錯就會從「直接選上」變成「已登記」**，這就是 0.9.2 修掉的 bug（實變函數論 536700）。

### 2.2 修課別與採計方式：伺服器照單全收

**實測 E13**：對一門必修課（516707，真實 `cos_type_code` 是 1）宣稱 `cos_type_code: '2'`，伺服器就把它記成**選修**。`wType` 送 `'9'` 則被忽略，存成 `X`（看起來 wType 會驗證是否為該課允許的值）。

**實測 E14（最重要）**：核心課程 534000 初等應用統計（基本素養-量性推理）：

| 送出的參數 | 記錄結果 |
|---|---|
| `cos_type_code: E`、`wType: E`、`category_type: DF91BC7C…`（正確） | 核心、brief `Z102`、群組 `51CE2C18…`（核心課程-**基本素養**） |
| `cos_type_code: 2`、`wType: X`、`category_type: ''` | **選修**、沒有 brief、**沒有志願群組** |
| `cos_type_code: E`、`wType: E`、`category_type: ''` | 核心、brief `Z102`、但群組變成 `6D27BD78…`（核心課程-**領域課程**） |

也就是說：

- **採計方式是在登記當下由我們送出的欄位決定的**，不是課本身固定的屬性。
- **漏掉 `category_type`，課會被丟進錯誤的志願群組**，而畫面上的 brief 還是顯示原本的類別，從結果幾乎看不出來。志願序是在群組裡比的，丟錯群組等於志願序算在別的地方。

**規則：這三個欄位一定要原封不動使用 `getregistrationcourselist` 在「使用者選的那條選單路徑」下回傳的值，絕對不能自己推論或留空。**

### 2.3 已經登記的課不能直接改志願

**實測 E6**：對已經登記的課再送一次 `setregist`（不管 wish 是什麼），一律回 `[{status:'error', cmsg:'重複選課'}]`。要改志願必須**先 `deleteregist` 取消，再重新 `setregist`**。

⚠️ 我們現在的「改志願」按鈕就是直接再送一次，實際上一定失敗。這是擴充功能要修的 bug。

### 2.4 伺服器擋什麼、不擋什麼

| 情況 | 伺服器 | 說明 |
|---|---|---|
| 沒有修課權限、課程未開放 | **擋**：`{status:'error', cmsg:'無權限加選，課號(…)', errortype:'nopriority'}` | 實測 535516 軟體測試、110044 臨床解剖學 |
| 人數已滿（70/70） | **不擋**，照樣登記 | 實測 561068 生死學 |
| 衝堂，且課有人數上限 | **不擋**，`getregistrationcourselist` 也回 success | 實測 515609（conflict_num 3） |
| 衝堂，且課不限人數 | **擋**，`status: error`、`cmsg: 衝堂…` | 實測 516714、534501 |
| 修課別、採計類別填錯 | **完全不擋** | 見 2.2 |
| 同一群組兩門課填同一個志願序 | 依群組而異 | 見 3.2、第 10 節 |
| 志願序送空字串或 0 | **完全不擋**（會存成 `" "` 或 `"0"`） | 見第 10 節，最危險的一條 |

推論：不限人數的課是「即選即上」，所以衝堂當下就擋；有上限的課是「登記後分發」，衝堂留到分發時處理。

## 3. 志願序群組（getCosCategoryWish）

### 3.1 資料結構

```
{ "<GroupUID>": {
    GroupName: "核心課程-基本素養", wType_cname: "核心課程",
    wish_limit: "6",     // 這個群組可以填幾個志願（多數 6，體育 5）
    cos_limit: "100",    // 這個群組最後可以選上幾門（學院共同／體育／微積分 = 1，核心／語言與溝通 = 100）
    wish: { "1": "0", "2": "0", "3": "2", ..., "F": "0" } } }
```

**`wish` 裡的值是「數量」，不是課號。**實測：在同一群組登記兩門課、都填第 3 志願之後，`wish["3"]` 從 `"0"` 變成 `"2"`。`wish.F` 則是這個群組已經**選上**幾門（實測帳號的微積分群組是 2、體育群組是 1）。

⚠️ 我們的 `wishOptions` 目前把這個值當成課號顯示「已填 563018」，是錯的。

選課網自己的用法（chunk-b47d6638）：

- 志願下拉選單只在 `wish.F <= cos_limit` 時出現，否則顯示「已達上限」。
- 每個志願序選項在 `wish[n] != 0` 時**變灰不能選**（已經用過的志願序不能重複用）。

### 3.2 重複志願：部分群組擋、部分不擋

**實測 E9**：同一個核心群組的兩門課（561068 生死學、534000 初等應用統計）都送第 3 志願，兩筆都成功，`wish["3"]` 變成 2。

⚠️ **第二輪修正（見第 10 節）**：這條規則依群組而異。學院共同那類（`cos_limit=1`）伺服器**會**擋，回 `重複登記志願(option to repeat)`；核心課程那類（`cos_limit=100`）**不擋**。所以不能假設任何一邊，程式要自己照選課網的前端規則擋，並且如實顯示伺服器的錯誤。

### 3.3 志願序在分發時的意義

API 沒有提供分發演算法。`getregistrationcourselist` 會回 `first_wish_reserved_num` 到 `fifth_wish_reserved_num`（各志願目前登記人數），可以顯示給使用者判斷。使用者提供的實務說法：同一門課若第一志願人數已超過上限，後面志願的人會直接被刷掉；因此**填錯志願序或沒填（被迫當成無志願）風險很高**。

## 4. 查詢（getregistrationcourselist）

- 參數：`cos_id` 加上選單路徑 `type / dep_category / college_no / dep_uid / group / grade / class`，以及 `category_type`。
- 回傳 `{ "<cos_id>": {...} }`；**查不到時回傳空陣列 `[]`**（例如選單路徑錯誤或該課不在那條路徑下）。
- 重要欄位：`status`（success/error）、`cmsg`、`cos_type_code`、`wType`、`GroupUID`、`num_limit`、`registered_num`、`conflict_num`、`first..fifth_wish_reserved_num`、`category_type`、`category_cname`、`brief`。
- **`blocked` 幾乎永遠是 `"1"`，不能拿來判斷能不能選**（實測 8 門課全部是 1，包含 status success 的）。要用 `status` 和 `cmsg`。
- `registered_num` 是登記人數，可能超過 `num_limit`（實測 516713 是 63/40）。自己登記之後這個數字不會立刻變動。

`preregistcourse`（列出某選單下的所有課）回傳的欄位更完整，包含 `brief`、`GroupName`、`category_*`、`crsoutline`、`classPri`、`degree`、`memo`。

## 5. 對「本機預排 + 一鍵匯出」架構的結論

### 5.1 可行，而且不需要碰預排

登記不需要預排（1.1）。所以本機清單可以直接匯出成一連串 `setregist`，預排只在「使用者想讓選課網自己的畫面也看得到」時才需要同步。

### 5.2 本機每一筆必須存什麼

因為採計方式是送出當下決定的（2.2），本機清單的每一筆都要存下**當初查詢時用的那條選單路徑**與**查到的結果**：

```
{ cosId, 選單路徑 menu{type,dep_category,college_no,dep_uid,group,grade,class},
  category_type, category_cname,        // 通識／核心類別，空字串也要明確存
  cos_type_code, wType,                 // 一律來自 getregistrationcourselist
  GroupUID, num_limit,                  // 決定送出時的 wish 規則
  wish,                                 // 有群組才需要，使用者選
  查詢時間 }
```

### 5.3 匯出前一定要重新查一次

存下來的值會過期（人數、開放狀態、甚至採計方式都可能被系所調整）。匯出流程應該是：

1. 對每一筆重新 `getregistrationcourselist`（用存下來的選單路徑）。
2. 查不到（回空陣列）或 `status` 是 error → **不要送**，明確告訴使用者哪一門、為什麼。
3. 查得到 → 用**這次查到的** `cos_type_code`、`wType`、`category_type` 組 `setregist`。
4. `wish` 依 2.1 的規則決定；有群組時要照 3.1 擋掉已用過的志願序。
5. 送出後**重新讀 `getregist` 驗證**，逐一比對 `sFlag` 是不是預期的值（不限人數應該是 `F`，其他應該是志願序或 `1`），把結果如實顯示。

### 5.4 絕對不能做的事

- 不能用預設值或猜測填 `cos_type_code`、`wType`、`category_type`。
- 不能在沒查到的情況下硬送。
- 不能對已經登記的課直接重送（會回「重複選課」）；改志願要先取消。
- 不能碰 `sFlag === 'F'` 的課。

## 9. 伺服器的錯誤類型（errortype）

| 情況 | 回應 |
|---|---|
| 沒有權限、未開放、課號不存在 | `{status:'error', errortype:'nopriority', cmsg:'無權限加選，課號(…)'}` |
| 志願序超出範圍（群組課送 wish=9，上限 6） | `{status:'error', errortype:'wish', cmsg:'志願登記超過規定數量(wrong option)'}` |
| 該群組已選滿（`wish.F > cos_limit`） | `{status:'error', errortype:'wish', cmsg:'該類課程加選數量超過規定(Exceed the upper limit)'}` |
| 同群組重複用同一個志願序（部分群組） | `{status:'error', errortype:'wish', cmsg:'重複登記志願(option to repeat)'}` |
| 已經登記過同一門課 | `{status:'error', cmsg:'重複選課'}`（沒有 errortype） |
| 取消沒登記的課 | `{status:'error', cmsg:'無此選課資料'}` |
| 預排重複加入 | `{status:'error', msg:'重複預選'}` |
| 預排加入不存在的課號 | `{status:'error', msg:'選課預選失敗'}` |
| 刪除不存在的預排 | `{status:'error', msg:'無此選課預選資料'}` |

注意「課號不存在」和「沒有權限」回應完全相同，程式無法分辨。

## 10. 志願序：三條伺服器規則、一條只有前端擋

| 規則 | 伺服器 | 實測 |
|---|---|---|
| 志願序必須在 1..`wish_limit` | **擋**（errortype wish） | 送 wish=9 被拒 |
| 群組已選滿（`wish.F > cos_limit`）不能再登記 | **擋** | 微積分群組（已選上 2 門、cos_limit 1）被拒 |
| 同群組不能重複用同一志願序 | **只有部分群組擋** | 學院共同（cos_limit=1）擋；核心課程（cos_limit=100）**不擋**，兩門課都停在第 5 志願 |
| 志願序送空字串或 0 | **完全不擋** | 見下 |

### ⚠️ 最危險的一條：空志願與志願 0

- 群組課送 `wish: ''` → **登記成功**，`sFlag` 存成 `" "`（一個空白字元）。
- 群組課送 `wish: '0'` → **登記成功**，`sFlag` 存成 `"0"`。

兩種都是選課網自己的畫面絕對不會產生的狀態，使用者在「已登記」清單裡也看不出異常，但分發時幾乎不可能選上。**我們的程式對有志願群組的課，必須強制使用者選 1..wish_limit 的值，絕不能送空值或預設值。**

## 11. 衝堂（conflict_num）只算「已選上」

實測：登記一門與 536712 同時段（T7）的課之後，536712 的 `conflict_num` 仍然是 3，沒有增加；取消後也一樣。

也就是 `conflict_num` 只計算 `sFlag='F'` 的課。我們自己的課表要標示「和已登記的課衝堂」的話，得自己算，選課網不會幫忙。

搭配第 2.4 節：衝堂只有在「不限人數」的課（即選即上）才會被伺服器擋；有上限的課照樣可以登記。

## 12. 登記階段沒有學分上限

實測帳號已選上 21 學分，逐步登記到 **39 學分**（6 門測試課），伺服器完全沒有抱怨。

所以學分上限是在分發或系辦端處理，登記階段不會擋。**匯出功能不能假設伺服器會保護使用者**，要自己算學分並提醒。

## 13. 換採計方式的正確程序

同一門課想改採計方式（例如核心改成選修）：

1. 直接重送 `setregist` → `重複選課`，失敗。
2. 必須 `deleteregist` 取消，再用新的 `cos_type_code`／`wType`／`category_type` 重新 `setregist`。

實測 534000：以核心登記 → 紀錄是 `cos_type_code E`、群組 `51CE2C18`；取消後以選修登記 → 紀錄變成 `cos_type_code 2`、**沒有群組**。

改志願也是同一套程序（取消再登記）。

## 14. getCosCategoryWish 是「最終一致」，不能馬上信

實測：登記第 2 志願後立刻讀，志願表還是全 0；取消之後那一筆才出現；再過幾秒才清掉。

所以：**寫入之後不要立刻用這張表判斷志願序有沒有被佔用**，要隔幾秒重讀，或以 `getregist` 的實際 `sFlag` 為準。`getregist` 是即時的。

## 15. preregistcourse 的 codition 只吃課號

實測：`codition='516703'` 回 1 筆；`'分析導論'`、`'Analysis'`、`'T34'` 都回 0 筆。課名搜尋要自己在本機做。

## 16. userinfo 就是「使用者自己的選單」

回傳 `type / dep_category / college_no / dep_uid / class / grade / group / degree / campus / enter_year / lastacysem / regist_acysem`，正好是查詢課程要用的那組選單欄位。這解釋了為什麼同一門課在不同人的帳號下會查到不同的採計方式。

## 17. 第二輪對匯出功能的補充規則

1. 有志願群組的課，**一定**要使用者明確選志願序，範圍 1..`wish_limit`；空值、0 都送得出去而且會毀掉那門課的分發機會。
2. 送出前先用 `getCosCategoryWish` 算好這個群組已經用掉哪些志願序（但剛寫入後要等幾秒再讀），並照 `wish.F > cos_limit` 顯示「已達上限」。
3. 匯出要自己算學分總和並提醒使用者，伺服器不會擋。
4. 衝堂要自己算，`conflict_num` 只含已選上的課。
5. 遇到 `errortype: 'wish'` 的錯誤要原文顯示給使用者，因為三種情況（超出範圍、群組滿、重複志願）處理方式不同。
6. 改採計方式或改志願一律是「先取消再登記」，中間那段時間課是沒有登記的，要提醒使用者風險（尤其接近關閉時間）。

## 21. 第三輪新增的結論

1. **`cos_type_code` 留空會被當成必修**。匯出時這個欄位絕對不能空著。
2. **`wType` 填錯或留空會讓志願群組消失**，課變成一般登記，志願序完全失效 — 而且伺服器回 success。
3. `category_type` 是三個欄位裡唯一會驗證的，但**留空不會被擋，只會進錯群組**。
4. `preregistcourse` 的 `codition` 是必填欄位，漏了會直接失敗。
5. `getregistrationcourselist` 的 `grade` 要用 `*`，填精確年級會查不到。
6. `getdep` 不能無參數呼叫。
7. `getsemregist` 空參數等於查當期。
8. 預排的空課號刪除不會誤刪全部，這點是安全的。

# 第四輪：對照學校公告的分發規則

學校公告的分發規則（使用者提供）：

> 依照「志願序(小到大)」、「優先序(大到小)」、「學生抽籤號(大到小)」順序，全部選課資料逐一分發。（非以志願序選課的一般課程預設為第一志願）
> 【志願序】第一志願至第五志願(不同類型志願數不同)，數字小者優先；【優先序】開課系所設定 5 至 1，數字大者優先；【學生抽籤號】送出時系統隨機給予，數字大者優先。
> 系統檢查項目：1. 有人數限制的課程是否超過限制 2. 限制修課數量的志願分發課程是否超過限制數量 3. 是否衝堂

## 23. 公告條文與實測的對照

| 公告 | API 上看到什麼 | 結論 |
|---|---|---|
| 志願序 1..5，不同類型志願數不同 | `getCosCategoryWish` 的 `wish_limit`，實測有 **5**（體育）和 **6**（其他）兩種 | 相符，但**上限可能是 6，不是公告寫的 5** |

| 優先序：開課系所設定 5 至 1 | `preregistcourse` 與 `getregistrationcourselist` 有 `classPri` 欄位 | 是這個欄位沒錯，但這個帳號只觀察到 **0 和 1** 兩種值（同一份系所清單裡兩種都有）。合理解讀是「這名學生對這門課的優先序」，0 代表沒有優先。**2–5 沒有觀察到，無法從單一帳號證實** |
| 學生抽籤號，送出時隨機給予 | `getregist` 的 40 個欄位裡**沒有任何抽籤號**；其他端點也沒有 | **查不到**。使用者無法知道自己的抽籤號，我們也不能顯示或預測 |
| 檢查 1：人數是否超過限制 | 登記階段**不擋**額滿（70/70 照樣登記成功） | 相符：這是分發時才檢查 |
| 檢查 2：志願分發課程的修課數量限制 | `cos_limit`；登記階段**就會擋**（`該類課程加選數量超過規定 Exceed the upper limit`） | 登記時和分發時都會檢查 |
| 檢查 3：是否衝堂 | 有人數上限的課登記時**不擋**衝堂；不限人數（即選即上）的課當場就擋 | 相符：有上限的課留到分發才檢查 |

## 24. 志願人數欄位確實可用

`first_wish_reserved_num` 到 `fifth_wish_reserved_num` 是**這門課目前各志願分別有幾個人登記**。實測 561068 生死學回 `[1,0,0,0,0]`，其他課目前多半是 0（加退選後期大家都已分發完）。

兩個限制：

- 只有五個欄位，但 `wish_limit` 可能是 6，**第六志願沒有對應欄位**。
- 數字會隨時間變動，要當成參考而不是保證。

這是我們可以合法顯示給使用者的「競爭程度」資訊：填志願時把各志願目前人數列出來，配合公告的分發順序（志願序小的先分發），使用者才知道填第幾志願才有機會。

## 25. 公告對匯出功能的影響

1. **`sFlag` 不是 1..6 的登記幾乎等於放棄**。公告的排序鍵是志願序，而空字串（`' '`）和 `0` 都不是合法志願序。實測這兩種都能送出成功（§10），所以我們必須在送出前自己擋掉，不能倚賴伺服器。
2. **一般課程不必也不能選志願**：伺服器會強制第一志願。UI 不該對這種課顯示志願選單（選課網也沒有）。
3. **優先序與抽籤號都不是我們能影響或顯示的**：優先序是系所設定（`classPri` 只看得到 0/1），抽籤號完全查不到。UI 不要假裝能預測分發結果。
4. **額滿與衝堂在登記階段不會被擋**：所以匯出後的驗證只能確認「有沒有登記成功」，不能確認「會不會選上」。回報文字要照這個區分寫，不能讓使用者誤以為已經選上。
